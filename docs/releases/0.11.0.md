gitd 0.11.0: a publish that updates its branch, and pull requests for submodules.

## Publishing again to the same branch

- `PublishRequest.update` (`--update`, `update=True`, `{ update: true }`, and
  `publish_branch`'s `update`): the branch may exist from an earlier publish. It moves only
  as a fast-forward, never forced, and the pull request open from it gets the new title and
  body instead of a second one being opened; `OpenedPullRequest.updated` says so.
- An update that brings nothing new beyond what gitd published to the branch pushes nothing
  and goes on to the pull requests. A publish whose pull request failed after the push, as
  when GitHub's API answered an error, is retried by publishing again, and no longer answers
  `NOTHING_NEW`. The rules still run and the audit log still records it.
- A pull request's body now counts the whole branch, the commits of earlier publishes
  included.

## Pull requests for submodules

- `PullRequestOptions.submodules` (`--submodules`): each submodule the branch changes gets
  its own pull request in its own repository, from the branch of the same name, with the same
  title, into the branch `.gitmodules` names for it, else its repository's default branch.
- They are opened first. The superproject's pull request lists them, to be merged first and
  each with a merge commit: it points at their new commits, which a squash or a rebase would
  replace. Each is then edited to link back to the superproject's.
- `PublishResponse.submodule_pull_requests` answers each one, or why it could not be opened:
  a submodule on a host other than GitHub, or one that cannot be reached, does not stop the
  others. The audit log keeps them too.

## Fixes

- A publish without update to a branch that already exists on the host is refused, as the
  contract always said: the push is now leased on the branch not existing. Before, git would
  move an existing branch when the push happened to be a fast-forward.

## Upgrading

The contract only grew (`buf breaking` against 0.10.0): two request fields, the response's
and the audit entry's `submodule_pull_requests`, `OpenedPullRequest.updated`, and the reason
`BRANCH_EXISTS`, which a publish to an existing branch now answers instead of `GIT_FAILED`.
Clients: `pip install gitd==0.11.0`, `npm install gitd-client@0.11.0`.
